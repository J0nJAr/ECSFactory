## 들어가며

11편은 화면에 쿼드 하나를 띄우고 이렇게 끝났다.

> **카메라가 없다.** 지금 화면에 그려지는 쿼드의 좌표는 NDC다. (…) **ECS와 아직 연결되지 않았다.**

이번 글에서 그 둘을 잇는다. 카메라를 만들고, ECS를 화면에 연결하고, 실제 키보드를 붙인다. 그러면 이 프로젝트가 열한 편 동안 준비해 온 장면이 나온다. **창을 두 개 띄우고, 한쪽에서 키를 누르면, 서버 확정을 거쳐 양쪽 화면의 캐릭터가 같이 움직인다.**

그런데 이 글의 무게중심은 다른 데 있다. 화면이 나온 다음에 곧바로 마주친 질문이 있었다.

> **두 화면이 같아 보이는데, 정말 같은 세계인가?**

캐릭터가 움직이는 걸 보는 것과 두 시뮬레이션이 일치한다는 걸 아는 것은 다른 일이다. 이 글의 절반은 그 차이를 다룬다. 그리고 그 과정에서 **화면만 봐서는 절대 못 찾을 버그**를 두 개 잡았다.

## 1. 카메라: 어느 평면을 보고 있나

직교 투영 카메라 자체는 간단하다. 어려운 결정은 **무엇을 화면에 매핑할 것인가**였다.

이 엔진의 이동 코드를 보면 답이 이미 정해져 있다.

```cpp
if (buttonMask & kInputMoveForward) { delta += Vector3::UnitZ(); }
```

"앞으로"가 **+Z**다. 즉 게임플레이는 XZ 평면에서 일어나고 Y는 높이축이다. 그러니 탑다운 카메라는 월드 X를 화면 가로로, 월드 **Z**를 화면 세로로 보내고 Y를 버려야 한다.

```
월드 +X → 화면 오른쪽
월드 +Z → 화면 위쪽      (DX11 NDC는 y가 위로 증가한다)
월드 +Y → 버림           (3D로 갈 때 이 자리에 진짜 투영이 들어온다)
```

설계 문서에는 카메라 필드가 `zoom`으로 적혀 있었는데 이름을 바꿨다. **"zoom이 크면 확대인가 축소인가"를 읽는 쪽이 매번 추측하게 된다.** 대신 `viewHeightWorldUnits`, 즉 "화면 세로에 월드 몇 유닛이 들어가는가"로 두었다. 방향이 하나뿐이라 틀릴 수가 없다.

### 카메라를 붙이자 드러난 결함

행렬을 만들어 넣기 직전에 문제를 발견했다. 11편에서 쓴 쿼드 확장 코드가 이랬다.

```cpp
auto corner = [&](float ox, float oy) {
    v.x = item.position.x + (ox * cosR - oy * sinR);
    v.y = item.position.y + (ox * sinR + oy * cosR);   // ← XY 평면
    v.z = item.position.z;
};
```

쿼드가 **XY 평면에 서 있다.** 그런데 카메라는 XZ를 투영하고 Y를 버린다. 그대로 두면 쿼드의 세로 방향이 통째로 사라져서 화면에 **선으로 찌그러진다.**

11편까지는 카메라가 항등 행렬이라 이게 드러나지 않았다. 좌표를 그대로 화면에 던지고 있었으니 XY든 XZ든 상관이 없었다. 카메라가 생기는 순간 둘 중 하나가 틀린 게 된다.

쿼드를 지면(XZ)에 눕히는 쪽으로 고쳤다. 탑다운 공장 게임에서 벨트나 기계는 바닥에 깔린 판이므로 그쪽이 맞고, 회전도 자연스럽게 Y축(수직축) 기준이 된다.

### GPU 없이 행렬 규약을 붙잡기

11편에서 행렬을 행 우선으로 저장하고 셰이더에 `row_major`를 명시하기로 정했다. 이 규약은 **한쪽만 틀려도 화면이 조용히 이상해지는** 종류다. 그리고 확인하려면 사람이 창을 띄워야 한다.

그래서 정점 셰이더가 하는 계산을 CPU에도 한 번 더 적었다.

```cpp
// mul(float4(pos, 1), M) 과 같은 계산.
const float x = p.x * m[0] + p.y * m[4] + p.z * m[8]  + m[12];
const float y = p.x * m[1] + p.y * m[5] + p.z * m[9]  + m[13];
```

이러면 단위 테스트가 규약을 지킨다. "월드 (10,0,0)이 NDC (1,0)으로 간다"를 GPU 없이 단언할 수 있다.

⚠️ 대신 함정이 하나 생긴다. **이 함수와 셰이더의 `mul`은 같이 고쳐야 한다.** 한쪽만 바꾸면 테스트는 통과하는데 화면은 틀린 상태가 된다. 그래서 두 곳 주석에 서로를 가리켜 뒀다.

## 2. ECS를 화면에 연결하기

`RenderSystem`이 하는 일은 한 줄로 요약된다.

```
View<Transform, Renderable> → DrawItem 목록 → IRenderer
```

여기가 **`Fixed64`에서 float으로 넘어가는 유일한 자리**이고, 방향은 한쪽으로만 간다. 이 시스템이 월드에 쓰기를 하지 않는 것이 그 보장의 실질적인 내용이라, 테스트로 못 박았다. 프레임을 세 번 돌려도 월드 해시가 변하지 않아야 한다.

### Present를 하지 않는다

`RenderSystem`은 `BeginFrame → SetCamera → Submit`까지만 하고 **`EndFrame`(Present)을 부르지 않는다.** 프레임을 닫는 것은 루프를 소유한 앱의 몫으로 뒀다.

이유는 나중에 UI가 들어올 자리 때문이다. 한 프레임에 월드를 그린 뒤 그 위에 UI 패스가 올라가야 하는데, 렌더 시스템이 Present까지 해버리면 **시스템 등록 순서가 곧 화면 순서가 되어버린다.** 그건 UI가 낄 자리를 없앤다.

### 가짜 백엔드로 테스트하기

`IRenderer`와 `IWindow`가 인터페이스라서, 제출된 `DrawItem`을 기록만 하는 가짜 구현을 만들 수 있다.

```cpp
class RecordingRenderer final : public EF::IRenderer {
    void Submit(const EF::RenderContext& context) override {
        submitted.assign(context.Items().begin(), context.Items().end());
    }
    // ...
};
```

이걸로 ECS 순회에서 `DrawItem`이 나오는 과정 전체가 GPU 없이 테스트된다. 10편에서 백엔드를 인터페이스 뒤에 둔 값어치가 여기서 돌아왔다.

### 스냅샷이 화면을 지운다

`Renderable`(색·크기)은 시뮬레이션 상태가 아닌 클라이언트 전용 표현이다. 그래서 스냅샷 대상에서 뺐다. 그랬더니 예상 못 한 일이 생겼다.

`World::ApplySnapshot`은 레지스트리를 **새로 만들어 통째로 교체한다.** 스냅샷에 없는 컴포넌트는 전부 날아간다는 뜻이다. 스냅샷은 조인과 resync에서 오므로, **접속 직후와 디싱크 복구 직후에 화면이 빈다.**

그래서 "없으면 붙인다"를 매 프레임 돌리게 했다. 그런데 이걸 앱 루프에 두었더니 캡처한 화면에서 플레이어가 사라지는 일이 생겼다. 한 번의 엔진 스텝 안에서 순서가 이랬기 때문이다.

```
FixedUpdate들 → 여기서 ApplySnapshot이 Renderable을 전멸시킨다
FrameUpdate들 → 여기서 RenderSystem이 그린다
```

앱 루프에서 스텝 **전에** 붙이면 "붙임 → 전멸 → 그리기"가 되어 그 프레임이 통째로 빈 화면이 된다. 표현 부착을 시스템으로 만들어 `RenderSystem`보다 먼저 등록하니 "전멸 → 붙임 → 그리기"가 되어 사라졌다.

한 프레임짜리 깜빡임이라 눈으로는 거의 안 보인다. 캡처가 하필 그 프레임에 걸려서 발견했다.

## 3. 화면만 봐서는 못 찾는 버그

여기가 이 글에서 제일 값어치 있는 부분이다.

카메라와 렌더 시스템을 만든 뒤, 다른 벤더의 모델에게 변경을 읽기 전용으로 검토시켰다. 세 가지를 지적받았고 그중 둘이 진짜였다.

### 클라이언트 전용 컴포넌트가 결정론 해시에 섞였다

`World::ComputeHash()`는 비트 복사 가능한 풀을 **전부** 섞는다. 그런데 `Renderable`도 그런 풀이고, **서버에는 이 풀이 아예 없다.**

귀결이 고약하다.

```
클라 해시 ≠ 서버 해시  (매 tick)
  → TickHash 비교가 디싱크로 판정
  → ResyncRequest
  → 전체 스냅샷 도착, 레지스트리 교체 (Renderable 전멸)
  → 표현 컴포넌트 다시 붙음
  → 또 불일치
```

**화면은 멀쩡한데 네트워크가 스냅샷만 실어 나르는 상태**가 된다. 캐릭터도 잘 움직이고 두 창도 비슷해 보이므로 눈으로는 알 수 없다.

고치는 방법은 어렵지 않았다. 표현 전용 타입을 해시에서 빼는 것이다.

```cpp
world.RegisterPresentationComponent<Renderable>();
```

중요한 건 **기본값의 방향**이다. 기본은 "해시에 포함"이고 이 함수는 명시적인 예외 선언이다. 반대로 만들면(등록해야 해시에 들어감) 깜빡 잊은 컴포넌트가 조용히 검증에서 빠지고, 그건 디싱크를 못 잡는 상태로 이어진다. **실수했을 때 시끄러운 쪽으로** 기본값을 정했다.

그리고 테스트를 두 개 넣었다. 등록하면 해시가 안 변한다는 것, 그리고 **등록하지 않으면 해시가 변한다는 것.** 두 번째가 없으면 첫 번째가 "해시 함수가 원래 그 컴포넌트를 안 본다"로도 통과해버린다.

### `ForEach`는 EntityId를 주지 않는다

두 번째 지적은 이거였다.

```cpp
view.ForEach([&](EntityId entity, Transform&, PlayerControl& control) { ... });
```

`ForEach`는 `EntityId`(64비트, version 포함)를 주지 않는다. **`EntityIndex`(32비트, version 없음)를 준다.** 그런데 `uint32_t`는 `uint64_t`로 암묵 변환되므로 **컴파일이 그냥 통과한다.**

만들어지는 것은 version 비트가 0인 가짜 id다. 갓 만든 엔티티는 version이 0이라 우연히 맞아떨어지고, **파괴 후 재사용된 index에서만 틀어진다.** 그때 `AddComponent`의 생존 단언이 터진다.

재현 조건이 "엔티티를 만들고 부수고 다시 만든 뒤"라서, 지금 테스트로는 안 걸린다. 반복자 경로(range-for)는 제대로 복원한 `EntityId`를 주므로 그쪽으로 바꿨고, 뷰 클래스 주석에 두 순회가 **서로 다른 타입을 준다**는 경고를 박아 뒀다.

## 4. 실제 키보드 붙이기

이제 입력이다. 열한 편 동안 테스트가 `QueueLocalInput`을 직접 불러 왔는데, 그 자리에 진짜 키보드가 들어간다.

### tick 단위로 넣는다

앱 루프는 모니터 주사율(보통 60~144Hz)로 돌고 시뮬레이션은 50Hz다. 프레임마다 입력을 큐에 넣으면 **같은 적용 tick을 겨냥한 입력이 여러 개 쌓인다.** 서버는 그 tick의 빈 슬롯 하나만 채우므로 나머지는 버려진다. 대역폭만 쓰고 얻는 게 없다.

그래서 엔진 tick이 바뀔 때만 하나 넣는다.

### 창이 둘이면 조작이 뒤엉킨다

이 엔진의 입력 계층은 `GetAsyncKeyState`를 쓴다. 그건 프로세스가 아니라 **시스템 전역의 키 상태**다. 창을 두 개 띄워 놓고 한쪽에서 W를 누르면 **두 클라이언트가 동시에 입력을 보낸다.**

`IWindow::HasFocus()`를 만들어 걸렀다. 근본 해결은 창 메시지 기반 입력으로 옮기는 것이고, 그건 콘솔 텍스트 입력을 만들 때 어차피 필요해진다. 그때까지의 임시 방편이다.

### 화면 밖으로 날아갔다

키를 붙이고 W를 1.5초쯤 누른 뒤 화면을 캡처했더니 **아무것도 없었다.**

버그처럼 보였는데 아니었다. 이동이 tick당 1유닛이고 tick이 50Hz라 **초당 50유닛**이다. 기본 시야가 세로 60유닛이니 0.6초면 화면을 벗어난다. 1.5초 눌렀으면 75유닛 위, 시야 밖이다.

카메라가 내 플레이어를 따라가게 했다. 카메라 위치는 순수하게 표현이라 해시에 들어가지 않으므로, **클라마다 카메라가 달라도 결정론은 그대로다.** 오히려 각자 자기를 따라가는 게 정상이다.

이걸로 이 프로젝트의 중간 결승선이 통과됐다. 내가 누른 키가 서버 확정을 거쳐 화면 속 엔티티를 움직인다.

## 5. 두 화면이 같은 세계인가

여기서 처음 질문으로 돌아온다.

두 창에 캐릭터가 나오고 잘 움직인다. 그런데 두 시뮬레이션이 정말 일치하는지는 **화면으로 알 수 없다.** 조금 어긋나 있어도 비슷해 보이고, 크게 어긋나면 그제서야 눈에 띈다.

이 엔진에는 이미 답이 있다. `World::ComputeHash()`가 tick마다 월드 체크섬을 낸다. 그걸 눈에 보이는 곳에 놓기만 하면 된다.

화면 안에 글자를 그리려면 드로우 목록과 폰트 아틀라스가 먼저 있어야 한다. 그건 아직 없다. 그런데 **제목 표시줄은 OS가 이미 그려 준다.**

```
ECSFactory [join] tick=1523 hash=36F0DEF161A59F3F
```

두 창을 나란히 놓고 같은 `tick`에서 같은 `hash`가 보이면 일치하는 것이다. 폰트 계층 없이 지금 쓸 수 있는 값싼 대체물이고, 화면 안 디버그 오버레이가 생기면 이 용도는 사라진다.

### 사람 손에서 떼어내기

제목을 눈으로 보는 것은 이 편까지는 통한다. 하지만 그러면 확인이 사람 손에 묶인다. 리팩터링할 때마다 창 두 개를 띄워 들여다봐야 한다.

자동화하려니 벽이 있었다. **실제 키보드 검증은 창 포커스에 묶여 있다.** 창이 둘이면 어느 쪽에 키를 줄지 OS가 정하고, 자동화 스크립트에서 포그라운드 전환은 신뢰할 수 없다.

그래서 가짜 키보드를 만들었다.

```
GameClient.exe --join 127.0.0.1 --input-script "100:W,120:"
```

tick 100에 전진, tick 120에 정지. **tick 기준이라 프레임률과 무관하게 매번 같은 결과가 나오고**, 실제 키보드와 같은 큐 경로를 탄다. 검증하는 길이 실제 길과 다르지 않다는 게 중요하다.

### 회선을 일부러 망가뜨리기

여기서 한 걸음 더 갔다. 재전송이나 재동기화 같은 복구 경로는 **정상 세션에서 한 번도 실행되지 않는다.** 실행되지 않는 코드는 조용히 썩고, 정작 필요한 날 처음 돌아간다.

실제 네트워크가 나빠지기를 기다리는 대신 주입하기로 했다.

```
--net-loss 30 --net-delay 1-4 --net-dup 5 --net-seed 20260823
```

손실 30%, 1~4틱 지터, 중복 5%. 마지막 인자가 핵심이다. **같은 시드 + 같은 트래픽이면 같은 손실 패턴이 나온다.** 재현되지 않는 실패는 고칠 수 없다.

지연을 시간이 아닌 **tick** 단위로 둔 것도 같은 이유다. 실제 시계를 쓰면 테스트가 진짜로 기다려야 하고 결과가 스케줄러에 따라 흔들린다. 재현성을 위해 만든 물건이 재현성을 깨면 곤란하다.

## 6. 측정한 것

| 상황 | 결과 |
|---|---|
| 깨끗한 회선, 같은 tick 표본 | 32개 전부 해시 일치 |
| 한쪽에 손실 30% + 지터 + 중복 | 31개 전부 일치, 디싱크 표시 없음 |
| 동시 캡처한 두 화면 | 921,600픽셀 중 0개 차이 |
| 실제 키보드 | 전진 비트가 잡히고, 카메라 추적 후 화면 중앙 유지 |

두 프로세스가 픽셀 단위로 같은 그림을 그린다는 것이 눈으로 확인됐다.

> ⚠️ 하나는 정직하게 적어 둔다. 손실을 넣어도 해시가 유지된 것은 **신뢰성 계층의 재전송이 먼저 복구했기 때문**이고, 재동기화 경로 자체의 복구력이 그 측정으로 증명된 것은 아니다. 그건 디싱크를 일부러 만들어서 따로 재야 한다.

## 마무리 / 남은 일

이번 편에서 화면과 시뮬레이션이 이어졌다.

| 한 일 | 왜 |
|---|---|
| 직교 카메라 | 월드 좌표를 화면에 매핑. XZ 평면을 보고 Y를 버린다 |
| `Renderable` + `RenderSystem` | ECS 순회에서 그릴 것이 나온다 |
| 실제 키보드 배선 | tick 단위, 포커스 게이트 |
| 카메라 추적 | 초당 50유닛이라 고정 카메라로는 0.6초면 시야를 벗어난다 |
| 창 제목에 tick·해시 | 폰트 없이 결정론을 눈으로 대조 |
| 스크립트 입력·링크 열화 주입 | 확인을 사람 손에서 떼어낸다 |

남은 것은 셋이다.

**보간이 없다.** 50Hz 시뮬레이션을 그대로 그리므로 빠르게 움직이면 끊겨 보인다. 이전 위치와 현재 위치를 누산기 비율로 섞어야 한다.

**접속이 여전히 비싸다.** 서버가 접속 처리 자리에서 곧장 엔티티를 만들고 있어서, 그 순간 서버의 엔티티 할당 상태가 클라들과 갈라진다. 수습은 재동기화가 한다. 즉 **누가 한 명 들어올 때마다 남은 전원이 전체 스냅샷을 한 번씩 받는다.** 결국 수렴하니까 넘어가고 있는 것이지 설계대로 도는 게 아니다. 건설(= 엔티티 스폰)이 필요한 공장 게임플레이를 시작하기 전에 반드시 정리해야 한다.

**재동기화 경로를 실제로 밟아 본 적이 없다.** 위에서 적었듯 지금까지의 측정은 재전송이 먼저 복구한 경우들이다. 디싱크를 일부러 만들어 탐지와 복구를 확인하는 장치가 필요하다.

다음 편은 그 셋 중 뒤의 둘을 다룬다. 디싱크를 주입해 보고, 거기서 나온 것들을 고치는 이야기다. 미리 말해 두면, **일부러 고장 내 보니 생각보다 많은 게 나왔다.**
