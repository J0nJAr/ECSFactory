# 부분 resync — 바뀐 풀만 보내고, 안 되면 전체 스냅샷

> 대상 독자: 이 작업을 **이어서 구현할 에이전트/개발자**.
> 상태: **N4.1~N4.4 완료.** 부분 resync가 동기화 시스템에서 동작한다. 마일스톤 표는 아래 §7.
> 관련 문서: [deterministic-input-lockstep.md](deterministic-input-lockstep.md)(lockstep 전체),
> [network-sync-system.md](network-sync-system.md)("delta snapshot은 별도 과제"로 남겨 둔 자리),
> [roadmap.md §9](roadmap.md) 의 N4(대규모 월드 비용).

---

## 1. 문제

디싱크가 나면 지금은 이렇게 복구한다.

```
클라: TickHash(T) 불일치 → ResyncRequest(T, localHash, remoteHash)
서버: 그 세 값을 읽지도 않고 → WorldSnapshot(월드 전체, tick = S - 1)
클라: ApplySnapshot → clientSimTick = S - 1
```

정확하지만 비싸다. 공장이 커지면 월드 전체 스냅샷은 수 MB가 되는데, 실제로 어긋난 건
**컴포넌트 한 종류**인 경우가 많다(예: 한 시스템의 비결정론 버그가 `Transform`만 망가뜨림).
게다가 이 비용은 디싱크가 날 때마다 반복된다.

## 2. 목표와 비목표

**목표**: 디싱크가 나면 **어긋난 컴포넌트 풀만** 보내서 고친다. 그걸로 안 고쳐지면
지금의 전체 스냅샷으로 **폴백**한다.

**비목표**:
- 정상 동작 중의 동기화 방식을 바꾸지 않는다. 정답은 계속 하나다 — **lockstep(확정 입력 중계)**.
  이 경로는 복구할 때만 쓴다.
- 조인은 계속 전체 스냅샷이다. 새로 들어온 클라는 비교할 상태가 없다.
- 엔티티 단위·바이트 단위 diff는 하지 않는다. 단위는 **컴포넌트 풀 하나**다(§4.3).

## 3. 버린 대안

### 3.1 "매 tick 변경분 스트리밍을 기본으로, lockstep을 폴백으로"

MMO식 상태 복제를 주 경로로 두자는 안이다. 버린 이유는 셋이다.

1. **정답이 둘이 된다.** 클라가 계산한 값과 서버가 보낸 값이 다르면 어느 쪽을 따르는가?
   서버 값을 따른다면 클라가 시뮬레이션할 이유가 없다.
2. **lockstep을 고른 이유가 사라진다.** 공장 게임은 매 tick 바뀌는 게 벨트 위 물건 전부다.
   "바뀐 것만"이어도 양이 많다. 입력만 보내서 아끼던 대역폭을 다시 쓴다.
3. **불변식 7과 충돌한다.** "클라 시뮬레이션은 확정 프레임이 구동한다." 시뮬레이션 도중에
   서버 상태를 끼워 넣으면 순서 통제가 깨진다.

경로가 둘이면 평소에 안 쓰는 쪽이 썩는다. resync 버그(스냅샷 tick 라벨 off-by-one)가
오래 숨어 있던 이유가 정확히 "정상 세션에서 안 밟혀서"였다.

### 3.2 서버가 tick별 월드 스냅샷 기록을 들고 있기

그러면 서버가 "클라가 불일치를 본 tick T의 상태"를 그대로 보낼 수 있어 tick 정렬 문제(§4.1)가
사라진다. 하지만 월드 전체를 tick마다 복사해 128 tick씩 들고 있는 건, 바로 우리가 줄이려는
"큰 월드" 비용을 메모리로 옮기는 것이다. 버렸다. (풀별 **해시**의 기록은 들고 있는다 — 그건 작다.)

### 3.3 왕복 두 번 (해시표 교환 → 필요한 풀 요청)

서버가 해시표를 보내고, 클라가 따라잡아 비교한 뒤, 다른 풀을 다시 요청하는 방식이다.
두 번째 요청을 받을 때 서버는 이미 더 앞 tick에 가 있어서, 결국 §3.2의 기록이 다시 필요해진다.
버렸다.

## 4. 고른 설계

### 4.1 핵심 함정 — 서버와 클라는 같은 tick에 있지 않다

resync 요청이 서버에 닿을 때 서버는 tick `S`를 처리 중이고, 클라가 불일치를 본 tick `T`는
그보다 과거다(`T < S`). 서버가 지금 상태의 풀을 보내면 그건 tick `S - 1`의 값이다.
**tick `T`에 멈춰 있는 클라의 다른 풀과 섞으면 서로 다른 시점의 상태가 한 월드에 공존한다.**

그래서 **클라가 서버 tick까지 따라잡은 뒤에** 갈아끼운다.

- 서버는 `X = SimulatedThroughTick(S) = S - 1` 시점의 풀을 보낸다(전체 스냅샷과 같은 라벨 계약).
- 클라는 그 패킷을 보류해 두고, 확정 `InputFrame`으로 평소처럼 시뮬레이션을 이어 가다가
  `clientSimTick == X`가 되는 순간 갈아끼운다.
- 클라가 `X`보다 앞서 있는 일은 없다. 서버는 tick `t`를 처리하면서 `InputFrame{t}`를 보내므로,
  tick `S` 시작 시점에 클라가 받을 수 있는 프레임은 `S - 1`까지다.

### 4.2 어떤 풀을 보낼지 — 풀별 해시 기록

어떤 풀이 어긋났는지는 **tick `T` 기준으로** 판정한다.

- 서버와 클라 모두 tick마다 **해시 분해표**를 기록한다(최근 128 tick, 기존 `kLocalHashHistoryTicks`와 같은 창).
  - `entityHash` — `EntityManager` 상태(next index / versions / free list)
  - `pools` — `TypeInfo::hash` 오름차순의 `(typeHash, poolHash)` 목록
  - `worldHash` — 위 둘을 순서대로 섞은 값. **`TickHash`가 싣는 바로 그 값이다.**
- 월드 해시를 풀 해시에서 유도하므로 tick당 해시 계산은 지금과 같은 한 번이다(이중 계산 없음).
- 클라는 `ResyncRequest`에 **tick `T`의 분해표**를 싣는다.
- 서버는 자기 기록에서 tick `T`의 분해표를 꺼내 비교하고, 다른 풀의 **현재(`X`) 값**을 보낸다.

### 4.3 왜 단위가 "풀"인가

- 해시를 이미 풀 단위로 돈다. 단위를 더 쪼개면(엔티티 청크) 해시 기록과 비교 비용이 늘어난다.
- 풀 하나를 통째로 갈아끼우는 건 `ApplySnapshot`의 검증 로직을 그대로 재사용할 수 있다.
- 더 쪼갤 필요가 생기면(풀 하나가 거대해지면) 그때 청크로 내린다. 이건 N4의 나머지(영역별 해시)와 같이 간다.

### 4.4 폴백 — 어디서 전체 스냅샷으로 넘어가는가

부분 resync는 "될 것 같을 때만" 쓰고, 조금이라도 의심스러우면 전체로 간다.

| 시점 | 조건 | 결과 |
|---|---|---|
| 서버가 요청을 받을 때 | tick `T`가 서버 기록 창 밖 | 전체 |
| 〃 | `entityHash`가 다름 (엔티티 할당이 갈라짐) | 전체 |
| 〃 | 풀 집합이 다름 (한쪽에만 있는 풀) | 전체 |
| 〃 | 다른 풀이 없음 (해시표는 같은데 월드 해시만 다름 — 있을 수 없는 상태) | 전체 |
| 클라가 `X`에서 적용할 때 | 클라의 `X` 시점 `entityHash` ≠ 서버가 실어 보낸 값 | 전체 요청 |
| 〃 | 풀 검증 실패 (죽은 엔티티 index, 타입 모양 불일치) | 전체 요청 |
| 〃 | 갈아끼운 뒤 `worldHash` ≠ 서버가 실어 보낸 `X` 시점 값 | 전체 요청 |

마지막 줄이 중요하다. **어긋남은 번진다.** `T`에서 `X`까지 클라가 망가진 풀로 시뮬레이션하는
동안, 그 풀을 읽는 시스템이 다른 풀까지 망가뜨릴 수 있다. 서버가 `T` 기준으로 고른 풀만으로는
부족할 수 있다는 뜻이다. 그래서 서버는 `X` 시점의 `entityHash`·`worldHash`를 함께 실어 보내고,
클라는 갈아끼운 **즉시** 검증한다. 다음 `TickHash`를 기다리지 않는다.

폴백 경로의 전체 스냅샷 요청은 기존 `WorldSnapshotRequest`를 그대로 쓴다.

### 4.5 와이어 변경

- `ResyncRequest`: `(tick, localHash, remoteHash)` 뒤에 tick `T`의 분해표가 붙는다.
- 새 패킷 `PartialSnapshot`(Reliable): `tick X`, `X` 시점의 `entityHash`·`worldHash`,
  그리고 `ComponentSnapshot` 목록(어긋난 풀만).
- 앱 레코드 배치가 바뀌므로 **`kReliabilityVersion`을 2 → 3으로 올린다.** 층 구분상 앱 계층
  버전이 맞는 자리지만 아직 없어서 여기서 막는 기존 관행(CLAUDE.md)을 따른다.

## 5. 지켜야 할 불변식

1. **부분 스냅샷의 tick 라벨도 `SimulatedThroughTick(tick)`이다.** 전체 스냅샷과 같은 계약이고,
   어기면 같은 off-by-one이 되살아난다.
2. **갈아끼우기는 `clientSimTick == X`에서만.** 다른 tick에서 끼우면 §4.1의 시점 혼합이 된다.
3. **월드 해시는 분해표에서 유도한다.** 두 계산 경로를 따로 두면 언젠가 어긋나고, 그러면
   풀 해시는 같은데 월드 해시만 다른 상태가 생긴다.
4. **분해표의 풀 순회 순서는 `TypeInfo::hash` 오름차순.** 기존 `ComputeHash`와 같은 이유다.
5. **표현 전용 컴포넌트(`RegisterPresentationComponent`)는 분해표에서도 빠진다.**
6. **전체 스냅샷이 오면 보류 중인 부분 스냅샷은 버린다.** 더 새로운 정답이 왔다.
7. resync in-flight 제한(한 번에 하나)은 부분·전체 모두에 걸린다.

## 6. 테스트 계획 (빨간불 먼저)

- 엔티티 상태만 다른 두 월드는 다른 해시를 낸다(N4.1).
- 분해표의 월드 해시는 풀 해시에서 유도되고, 타입 첫 사용 순서와 무관하다(N4.2).
- **부분 경로가 실제로 밟히는가**: 클라의 `Transform` 하나를 망가뜨리면 부분 resync로 수렴하고,
  전체 스냅샷 적용 횟수는 늘지 않는다(N4.4).
- **폴백 경로가 실제로 밟히는가**: 클라의 `EntityManager`를 갈라 놓으면 전체 스냅샷으로 수렴한다.
  번짐(갈아끼운 뒤 해시 불일치) 경로도 주입해서 확인한다(N4.4).
- 기존 디싱크 테스트(`Network.DesyncRecoversWhileWorldKeepsMoving` 등)는 그대로 통과해야 한다.

⚠️ 폴백이 잘 될수록 평소엔 안 밟힌다. 폴백 테스트는 **반드시 주입으로** 경로를 강제한다.

## 6.5 남은 것과 알려진 한계

- ~~**전체 스냅샷 자체가 64KB를 넘으면 보낼 수 없다.**~~ → N4.5에서 신뢰 레코드 상한을 16MiB로 바꿨다. 다만 실제 UDP에서의 버스트 손실은 N4.6에서 다룬다.
  (원래 기록:) **전체 스냅샷 자체가 64KB를 넘으면 보낼 수 없다.** `NetworkManager::SendPacket`이 앱 레코드
  페이로드를 `uint16_t` 최대(65535바이트)로 막는다. 부분 resync는 평소 복구의 크기를 줄여 주지만,
  폴백(전체 스냅샷)과 **조인**은 여전히 이 한계에 걸린다. 큰 공장에서는 조인부터 실패한다.
  스냅샷 분할 전송(N4의 다음 조각)이 필요하다. → [large-record-transport.md](large-record-transport.md)(N4.5~N4.7).
- **부분 스냅샷 하나도 64KB에 걸린다.** 풀 하나가 그보다 크면 같은 문제다. 그때 풀을 청크로
  쪼개는 것(§4.3)을 함께 한다.
- **실행 파일에 디싱크 주입 옵션이 없다.** 부분 경로·폴백 경로는 테스트 주입으로만 밟는다.
  실제 창 세션에서 보려면 `GameClient`에 주입 인자(예: `--desync-at N`)를 하나 둘 수 있다.
- `ResyncRequest` 백오프는 여전히 없다(CLAUDE.md "미완성" 목록).

## 7. 마일스톤

| 기호 | 무엇 | 상태 |
|---|---|---|
| N4.1 | `ComputeHash()`에 `EntityManager` 상태를 넣는다 | ✅ |
| N4.2 | 해시 분해표(엔티티·풀별·월드) + 양쪽 tick별 기록. 월드 해시를 분해표에서 유도 | ✅ |
| N4.3 | 데이터 계층: `ResyncRequest`에 분해표, `PartialSnapshot` 와이어 포맷, `World::CreatePartialSnapshot`·`ApplyPartialSnapshot`(전부 아니면 전무), `SelectPoolsForPartialResync`. `kReliabilityVersion` 3. **서버 응답은 아직 전체 스냅샷** | ✅ |
| N4.4 | 동기화 시스템 연결: 서버가 부분 응답, 클라가 `X`에서 갈아끼우고 즉시 검증, 실패 시 전체 폴백. 주입 테스트 셋(부분 / 서버 쪽 폴백 / 클라 쪽 폴백) | ✅ |

> **N4.3/N4.4 경계를 처음 계획에서 옮긴 이유.** 처음엔 N4.3에서 서버의 부분 응답까지 켜려 했다.
> 그러면 클라가 아직 `PartialSnapshot`을 모르는 중간 커밋에서, 클라가 그 패킷을 버리고
> resync in-flight 플래그가 영영 내려가지 않아 **복구가 멈춘다.** 기존 복구 테스트가 그 커밋에서
> 깨진다. 그래서 N4.3은 "부품"(데이터 계층)만 만들고, 서버 응답과 클라 적용은 N4.4에서 한꺼번에 켠다.
> 커밋마다 전체 테스트가 초록으로 남는다.
