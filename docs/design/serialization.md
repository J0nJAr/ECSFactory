# 직렬화 설계서 — 리플렉션과 JSON

> 대상 독자: 이 계층을 구현할 에이전트/개발자.
> 관련: [roadmap.md](roadmap.md)(트랙 S), [deterministic-input-lockstep.md](deterministic-input-lockstep.md)(와이어 포맷의 결정론 제약).
> 동기: **AI가 읽을 수 있는 저장 방식**. AI 시대에 상태를 사람·도구·AI가 그대로 읽을 수 있어야 한다는 판단.

---

## 0. 이건 한 가지 질문이 아니다

용도마다 요구가 정반대다. 하나로 통일하면 어느 쪽이든 손해를 본다.

| 갈래 | 예 | 지배적 요구 | 결론 |
|---|---|---|---|
| ① 와이어(네트워크) | `WorldSnapshot`, `InputFrame`, `TickHash` | 50Hz 대역폭, **비트 단위 결정론** | **바이너리 고정. 논의 대상 아님** |
| ② 세이브(월드 상태) | 매치 저장, 재시작 복원 | 정확성 + 크기, 가끔 사람이 봄 | 바이너리 정본 + JSON 덤프 |
| ③ 저작 문서 | UI 레이아웃(X4), 프리팹, 씬 | **diff · 손편집 · AI 읽기** | JSON 정본 |
| ④ 설정 | 키 바인딩, 엔진 config | 사람이 직접 고침 | JSON 정본 |

①을 텍스트로 바꾸는 일은 없다. `Fixed64`의 raw 비트를 그대로 나르는 것이 결정론의 근간이고, 매 tick 도는 경로다.

## 1. 진짜 병목은 포맷이 아니라 리플렉션이다

`TypeInfo`가 아는 것은 `{hash, index, name, size, alignment, isTrivial}`뿐이다. 컴포넌트는 `IPool::GetRawBytes()`로 **불투명한 바이트 덩어리**로 다뤄진다. 엔진은 어떤 필드가 어디에 있는지 모른다.

그래서 리플렉션 없이 JSON을 고르면 이런 것이 나온다.

```json
{ "Transform": { "entities": [1,2,3], "bytes": "00000001a3f9...4c2e" } }
```

**바이너리보다 나은 점이 하나도 없다.** 크기만 2배다.

> 즉 실제 질문은 "바이너리냐 JSON이냐"가 아니라 **"컴포넌트 필드 리플렉션을 넣느냐"**다.
> 리플렉션이 있으면 어떤 포맷이든 싸게 뽑을 수 있고, 없으면 어떤 포맷을 골라도 hex 덩어리다.

그리고 이건 추가 작업이 아니다. [roadmap.md §10](roadmap.md)의 **X1 인스펙터**("실행 중 엔티티/컴포넌트 값 보기")가 정확히 같은 것을 요구한다. 한 번 만들면 인스펙터 · JSON 덤프 · 에디터 편집 · 세이브가 전부 딸려온다.

## 2. 리플렉션 — 어떻게 적고 무엇이 만들어지나

두 가지 접근이 흔히 대비되지만, **"어떻게 적느냐"와 "무엇이 만들어지느냐"는 다른 축**이다.

### 2.1 수동 등록 (매크로 + 멤버 포인터, 컴파일 타임)

```cpp
EF_REFLECT(Transform, position, rotation)   // 멤버 포인터 목록을 만든다
```

- ✅ **타입 안전.** 필드 이름을 바꾸면 컴파일이 깨진다. 조용히 틀리지 않는다.
- ✅ 중첩이 자연스럽다(`Vector3` → `Fixed64` → `int64` 재귀).
- ❌ 매크로라 읽기·디버깅이 불편하다.
- ❌ **컴파일 타임 전용.** `TypeInfo.hash`만 아는 런타임 상황에서 필드를 열거할 수 없다. ← 이 엔진에는 치명적이다. 스냅샷·풀·인스펙터가 전부 런타임 순회다.

### 2.2 서술자 테이블 (offsetof + 런타임 데이터)

```cpp
enum class FieldKind { Int32, UInt32, Int64, UInt64, Fixed64, Vector3, Quaternion, /* ... */ };

struct FieldDesc {
    const char* name;
    FieldKind   kind;
    std::size_t offset;   // offsetof(Transform, position)
    std::size_t size;
};

struct ComponentReflection {
    TypeInfo               type;
    std::vector<FieldDesc> fields;
};
```

- ✅ **엔진의 기존 모양에 맞는다.** 이미 raw 바이트 + 런타임 `TypeInfo`로 돌아간다.
- ✅ 함수 하나가 모든 컴포넌트를 처리한다(템플릿 폭증 없음).
- ✅ **테이블이 데이터라 해시를 낼 수 있다.** → §5 참조. 접속 시 필드 구성 불일치까지 잡을 수 있다.
- ✅ 필드별 메타데이터(에디터 표시 이름, 범위, 편집 위젯 힌트)를 붙일 자리가 생긴다.
- ❌ 정적 타입 안전성 상실 — `FieldKind`를 잘못 적어도 컴파일은 통과하고 런타임에 값이 깨진다.
- ❌ `FieldKind` enum을 지원 타입마다 유지해야 한다.

### 2.3 채택 — 매크로로 적고, 런타임 테이블을 만든다

둘은 배타적이지 않다. **표기는 2.1, 산출물은 2.2.**

```cpp
// 적는 건 이것뿐
EF_REFLECT(Transform, position, rotation)

// 매크로가 만드는 것:
//   name   ← #member (전처리기)
//   offset ← offsetof(T, member)            (컴파일러가 계산)
//   size   ← sizeof(decltype(T::member))
//   kind   ← FieldKindOf<decltype(T::member)>::value
```

`FieldKindOf<T>`는 지원 타입마다 특수화된 trait이다. **특수화가 없는 타입을 쓰면 컴파일 에러**가 난다 — 2.2의 "잘못된 kind를 손으로 적을 수 있다"는 단점이 사라진다. 필드 이름도 한 곳에만 쓴다.

**제약과 근거:**
- `offsetof`는 표준상 standard-layout 타입에만 보장된다. 우리 컴포넌트는 스냅샷 대상이라 이미 **trivially-copyable을 static_assert**하고 있고 실제로 단순 POD다. 리플렉션 등록 시에도 같은 static_assert를 건다.
- 리플렉션은 **스냅샷 대상 컴포넌트에 대해 선택이 아니라 의무**로 둔다. 새 컴포넌트를 만들 때 같이 적지 않으면 나중에 전수조사가 된다.

## 3. 어떤 JSON인가 — 방향에 따라 다르게

호환성 걱정의 해법은 **쓰는 쪽과 읽는 쪽을 비대칭으로** 두는 것이다. 우리가 둘 다 통제하므로 가능하다.

| 방향 | 방언 | 이유 |
|---|---|---|
| **출력(쓰기)** | **엄격 RFC 8259.** 주석·끝단 콤마 절대 안 쓴다 | `jq`, `JSON.parse`, python, AI 도구, diff 뷰어가 전부 읽는다. **호환성 위험 0** |
| **입력(읽기)** | **관대.** 끝단 콤마 + `//`, `/* */` 주석 허용 | 손편집·AI 편집이 편하다. 콤마 하나로 로드가 깨지지 않는다 |

### 확장자로 방언을 구분한다

| 확장자 | 누가 쓰나 | 방언 |
|---|---|---|
| `.jsonc` | **사람**(설정, UI 레이아웃, 프리팹) | 주석·끝단 콤마 OK |
| `.json` / `.jsonl` | **기계**(월드 덤프, 세이브 사이드카) | 항상 엄격 |

`.jsonc`는 VS Code가 이미 아는 확장자다(tsconfig가 같은 방언). 새 표준을 발명하는 게 아니다.

> ⚠️ **감수할 것:** 사람이 `.jsonc`에 단 주석은 엔진이 그 파일을 다시 쓰면 날아간다.
> 그래서 규칙: **손으로 쓰는 파일은 엔진이 자동으로 덮어쓰지 않는다.**
> 에디터가 UI 레이아웃을 저장하는 경우(X4)는 예외이고, 그건 X4에서 판단한다.

**JSON5를 안 쓰는 이유:** 따옴표 없는 키·16진수·홑따옴표까지 가면 사실상 다른 언어가 되고, 표준 도구가 못 읽는다. 우리가 원하는 건 "편집 편의"지 "새 문법"이 아니다.

### ⚠️ int64 함정 (이 프로젝트에 직접 걸린다)

많은 JSON 파서가 숫자를 `double`로 처리해 2^53(약 9.0e15)을 넘으면 비트가 깨진다.

- `Fixed64`는 Q32.32라 raw = 값 × 2^32. 값이 약 ±2^21(≈210만)을 넘으면 raw가 2^53을 넘는다. 공장 게임 그리드에서는 웬만해선 안 넘지만 **보장은 없다**.
- `ComputeHash()` / `TickHash`는 **FNV-1a 64비트**다. 일상적으로 2^53을 넘는다. **확실히 안전하지 않다.**

**규칙:** raw 정수와 해시는 **문자열로 쓴다.** 리더는 문자열과 숫자를 둘 다 받는다.

```json
{ "position": { "x": { "raw": "4294967296" }, "y": { "raw": "0" } } }
```

읽기 편의를 위해 사람용 필드를 **덤프에 한해** 곁들일 수 있다(`"approx": 1.0`). 이건 **읽기 전용 참고값**이고 로드 시 무시한다 — 정본은 언제나 `raw`다.

## 4. 엔티티 덤프는 JSONL

통짜 JSON 하나보다 **한 줄에 엔티티 하나**가 낫다.

- `grep`이 된다
- 스트리밍으로 읽고 쓴다(수만 엔티티에서 중요)
- diff가 줄 단위로 깔끔하다
- **AI가 부분만 읽어도 유효하다** — 통짜 JSON은 잘리면 파싱이 불가능하다

```jsonl
{"entity":1,"Transform":{"position":{"x":{"raw":"0"},...}},"PlayerControl":{"clientId":1}}
{"entity":2,"Transform":{...},"Velocity":{...}}
```

## 5. 덤으로 얻는 것 — 스키마 해시

리플렉션 테이블은 데이터이므로 **해시를 낼 수 있다**(필드 이름·kind·offset·size의 FNV-1a).

지금 `TypeTable` handshake는 `hash`/`size`/`alignment`/`isTrivial`만 비교한다. 즉 **크기가 같고 필드 구성만 다른 변경**(예: `Vector3 position; Vector3 velocity;` 순서 바꿈)을 못 잡는다. 접속은 성공하고 스냅샷이 조용히 엉킨 채 적용되어, 원인이 먼 곳에서 해시 불일치로 나타난다.

스키마 해시를 타입 테이블에 추가하면 이걸 **접속 시점에** 잡는다. S 트랙 후반부에 넣는다.

## 6. 마일스톤 (트랙 S)

| # | 산출물 | "됐다"의 기준 |
|---|---|---|
| **S1** | JSON 라이터(엄격 출력). 의존 0, **쓰기 전용** | 중첩 객체·배열·문자열 이스케이프가 표준대로 나온다. `jq`가 읽는다 |
| **S2** | `EF_REFLECT` + `FieldKindOf` + 런타임 `ComponentReflection` 테이블. 기존 컴포넌트 전부 등록 | 런타임에 `TypeInfo.hash`로 필드 목록을 얻는다 |
| **S3** | 월드 → JSONL 덤프 + 콘솔 명령 `dump` | 실행 중 월드를 파일로 뽑아 사람이·AI가 읽는다 |
| **S4** | 관대한 JSON 파서(끝단 콤마 + 주석) | 주석·끝단 콤마가 든 `.jsonc`를 읽는다. 엄격 파일도 당연히 읽는다 |
| **S5** | 설정 로드(`.jsonc`) — 키 바인딩 등 | 파일을 고치면 다음 실행에 반영된다 |
| **S6** | 세이브/로드 — 바이너리 정본 + 선택적 JSON 사이드카 | 월드를 저장하고 껐다 켜도 **해시가 같다** |
| **S7** | 스키마 해시를 `TypeTable` handshake에 추가 | 필드 구성이 다른 클라가 **접속 단계에서** 거부된다 |

**순서상의 위치:** S2(리플렉션)를 **트랙 G(공장 게임플레이)보다 먼저** 둔다. G가 컴포넌트를 여럿 새로 만드는데, 그때 리플렉션이 이미 있으면 처음부터 갖고 태어난다. 나중에 소급하면 전수조사가 된다.

S1과 S2만 있으면 S3이 바로 따라오고, 그때 이미 "AI가 읽을 수 있다"는 목표는 달성된다. S4 이후는 저작·설정용이다.

## 7. 아직 정하지 않은 것

| 열린 질문 | 언제 정하나 |
|---|---|
| 비trivial 컴포넌트(문자열·컨테이너)의 직렬화 | 실제로 그런 컴포넌트가 필요해질 때. 지금은 스냅샷 대상이 전부 trivial이다 |
| 세이브의 하위 호환(옛 세이브 읽기) | 세이브가 사용자에게 의미를 갖기 시작할 때. 그전엔 버전 불일치 = 거부로 충분 |
| `.jsonc` 저장 시 주석 보존 | X4(UI 에디터)에서 에디터가 파일을 다시 쓸 때 |
| 덤프의 `approx` 사람용 필드를 넣을지 | S3에서 실제로 읽어보고. 없으면 불편한지 재고 판단 |
| 바이너리 세이브를 아예 JSON으로 대체할지 | S6에서 실제 크기·속도를 재고. 소규모면 JSON 정본도 선택지다 |
