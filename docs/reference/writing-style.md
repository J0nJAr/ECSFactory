# 블로그 글 문체 기준

블로그에 올리는 글(`docs/blog/*.md`, 복습 문서)에 적용한다. 설계 문서나 코드 주석은 대상이 아니다.

## 왜 이 문서가 있나

이 시리즈의 초안은 에이전트가 쓰고, 저자가 **"AI 티가 나는" 표현을 덜어낸 뒤** 발행한다.
그 손질이 매번 반복되는 수작업이라, 무엇을 얼마나 덜어내는지를 수치로 못박아 둔다.

한 번 겪은 실패가 있다. "줄여라"라고만 지시하면 **0에 가깝게 깎는다.** 그것도 손댄 티가 난다.
그래서 기준은 상한과 하한을 함께 둔다.

## 기준값

**산문 1만 자당 허용 상한**이다. 산문은 코드 블록과 인라인 코드를 걷어낸 본문을 말한다.
**하한은 없다. 0이어도 통과다.**

| 패턴 | 상한 |
|---|---|
| em dash `—` | **2.0** |
| `A가 아니라 B다` | 2.4 |
| `~가 아니다` | 0.4 |
| `정확히` | 0.5 |
| `~인 셈이다` | 0.7 |
| `바로 그/이` | 0.2 |
| `~일 뿐이다` | 0.5 |

### 이 숫자가 뜻하는 것

산문 1만 자에 몇 번 나오는가다. 원고지로 치면 50장이다.
`em dash 2.0`은 **1만 자에 두 번**, 즉 원고지 25장에 한 번꼴이다.

정리 전 상태를 같은 단위로 보면 감이 온다.

```
07편 원고   산문 15,573자에 대시 51개  →  32.7   약 300자마다 한 번 (원고지 한 장 반)
09편 원고   산문  6,529자에 대시 16개  →  24.5   약 400자마다 한 번
```

### 이 상한은 발행본 실측치가 아니다

발행본 1~6편(`machamy.tistory.com/28`~`/33`)을 같은 방식으로 재면 **em dash 8.3 / `A가 아니라 B` 6.8**이
나온다. 그 글들도 손질을 거쳤지만 구문이 꽤 남아 있어서, 그 밀도를 따라가면 덜어낼 이유가 없어진다.
그래서 상한은 발행본보다 낮게 잡았다.

> ⚠️ **기준을 다시 잴 일이 있으면 분모를 맞춰라.**
> 한 번은 기준을 코드 포함으로 재고 측정을 코드 제외로 재서 목표치가 3배 어긋났다.
> `tools/check-writing-style.py` 의 `prose_of()` 와 **똑같은 방식**으로 재야 한다.

> ⚠️ **하한을 두지 않는 이유.** 예전에는 "너무 깎는 것도 티가 난다"고 보고 하한을 뒀는데,
> 그 결과 *줄여라 → 너무 깎았다 → 되살려라*를 두 바퀴 돌았다. 왕복 비용이 얻는 것보다 컸다.

## 도구를 이겨서는 안 되는 자리

이 검사는 **문장을 더 낫게 만들려고** 있는 것이지 통과시키려고 있는 게 아니다.
아래는 한도를 넘더라도 고치면 안 되는 자리다.

**인용문.** 앞 글이나 코드 주석에서 그대로 옮긴 문장은 원문 그대로여야 한다.
실제로 한 번 이런 일이 있었다. 6편의 절 제목 `## UDP는 아직 완성형이 아니다`가 `~가 아니다`
한도에 걸리자 `완성형에 못 미친다`로 고쳤는데, **7편이 그 문장을 인용하고 있었고 6편은 이미 발행된
상태였다.** 결과적으로 발행된 원문과 다른 말을 인용하게 됐다. 게다가 다른 에이전트가 그 임시 문구를
원문으로 오인해 복습 문서까지 따라 고쳐, 같은 인용이 세 가지 표기로 갈렸다.

지금은 `> ` 인용 블록과 `<blockquote>` 를 측정에서 뺀다. 그래도 **본문 안의 인용과 인용된 제목은
여전히 잡히므로**, 아래 두 곳은 알면서 남긴 위반이다.

| 파일 | 걸리는 것 | 왜 남기나 |
|---|---|---|
| `docs/blog/06_*.md` | 절 제목 `UDP는 아직 완성형이 아니다` | 발행된 6편의 제목이고 7편이 인용한다 |
| `docs/blog/07_*.md` | 본문 안의 같은 문장 인용 | 위 제목의 인용이다 |

**조사만 바꿔 검출을 비껴가는 것도 하지 마라.** `패킷이 아니다` → `패킷은 아니다` 같은 변경은
숫자만 내리고 문장은 그대로다. 정규식으로 문체를 재는 방식의 한계이지, 통과했다고 나아진 게 아니다.

## 재는 법

```bash
python tools/check-writing-style.py --all-blog             # docs/blog/*.md 전부
python tools/check-writing-style.py docs/blog/08_*.md      # 파일 지정
python tools/check-writing-style.py ~/Documents/explanations/blog-0*.html
```

기준을 벗어난 항목이 있으면 종료 코드 1을 낸다. CI 에 걸고 싶으면 이걸 쓰면 된다.

측정에서 **mermaid 블록과 코드 블록은 제외**한다. 다이어그램 라벨의 부호는 산문 습관이 아니고,
코드 주석은 코드다.

하한은 **그 패턴이 이 길이에서 여러 번 나올 만할 때만** 본다. 3천 자짜리 글에서
"1만 자당 0.5를 못 채웠다"는 판정은 뜻이 없기 때문이다.

## 고칠 때 지킬 것

**기계적으로 치환하지 않는다.** `—` 를 전부 쉼표로 바꾸면 숫자만 내려가고 글은 나빠진다.
그리고 새 습관(모든 자리에 콜론, 모든 자리에 괄호)이 생기면 똑같이 티가 난다.
실제로 쓸 수단은 이렇다.

- 두 문장으로 끊는다
- 삽입구를 괄호로 넣는다
- 쉼표로 잇는다
- 부연이 필요 없으면 뺀다 (군더더기였던 경우가 많다)
- 어순을 바꿔 부연을 주절로 올린다

`A가 아니라 B다` 는 **긍정문이 기본**이다. "X는 Y다"로 쓴다.

### 대시를 남겨야 하는 자리

전부 없애면 안 된다. 아래는 대시가 실제로 제값 하는 자리다.

| 쓸 자리 | 예 |
|---|---|
| 강한 단정 뒤 짧은 단서 | `실제로는 절반만 되어 있었다 — 그 이야기는 4절에 있다.` |
| 긴 논증의 마무리 요약 | 앞 문단 전체를 한 줄로 접을 때 |
| 열거를 받는 마무리 | `시간, 난수, 프레임률, tick 번호 — 어느 것에도 의존하지 않는다.` |
| 갑작스러운 방향 전환 | `결국 따라잡는다 — 하지만 이 몰아 적용이…` |
| 근거 후치 | 결론을 먼저 던지고 이유를 뒤에 붙일 때 |

한 절에 하나 정도로 분산한다. 한 문단에 몰리면 그것도 티가 난다.

### 부정형을 남겨야 하는 자리

`A가 아니라 B다` 를 전부 없애면 **흔한 오해를 바로잡는 문장의 힘이 사라진다.**
대조 자체가 정보인 자리는 남긴다. 실제로 남긴 예:

- `정적 링크는 "공유"가 아니라 "복사"다` — 입문자가 가장 자주 틀리는 지점
- `서버 권위는 빌드 시스템이 보장하는 속성이 아니라 실행 경로와 규칙으로 유지되는 속성이다`
- `판정 근거는 각 ComponentSnapshot의 descriptor지, 따로 받은 TypeTable 패킷이 아니다`
- `실패의 모양이 "ABA 부활"이 아니라 "생존 판정 붕괴"다` — 앞 문단이 깔아 둔 반전 지점
- 퀴즈 오답 해설 — "무엇이 아닌지"가 곧 해설 내용이다

판단 기준은 하나다. **그 부정이 독자의 오해를 실제로 막고 있는가.** 아니면 긍정문으로 바꾼다.

## 이 기준에 없는 것

문장 길이, 존댓말/반말, 절 구성 같은 것은 재지 않는다. 시리즈 기존 글을 따르면 된다
(반말 서술체, 1인칭, "~다"체). 새 글을 쓸 때는 발행본 한 편을 열어 놓고 쓰는 편이 빠르다.
